# Governance

## Project model

Synara is an open-source project with maintainer-led technical direction.
Contributions are welcome, but maintainers are responsible for the product's
scope, architecture, security, release quality, and long-term maintenance
cost.

This means that a technically correct contribution may still be declined when
it conflicts with the current direction, duplicates planned work, or creates
maintenance costs that the project cannot support.

## Maintainers

Maintainers have write access and are responsible for:

- setting and communicating project direction;
- triaging issues and pull requests;
- reviewing architecture and security-sensitive changes;
- protecting contributor and user data;
- managing releases and repository automation;
- adding or removing maintainers.

The current maintainer authority is represented by the repository owner and
configured GitHub permissions. Changes to that arrangement should be recorded
in this document or a linked project decision.

## Decision making

Small bug fixes, documentation corrections, and maintenance changes can usually
be proposed directly as issues or pull requests.

Large features, architecture changes, provider integrations, and changes to
security or data boundaries should begin with a written proposal. The proposal
should explain the problem, intended users, alternatives, scope, risks, and
verification plan. Maintainers may request a smaller experiment before
approving implementation.

Maintainers make the final decision after considering evidence, project
principles, implementation cost, and community feedback.

## Contribution path

The expected path is:

1. search existing issues and documentation;
2. open an issue for a non-trivial idea or unclear direction;
3. get confirmation that the direction is wanted;
4. make a focused change;
5. open a pull request with verification evidence;
6. respond to review and keep the change scoped.

Opening a pull request does not guarantee review or acceptance. Maintainers
should still communicate decisions clearly and avoid hostile or personal
language.

## Changes to governance

Changes to this document should be proposed through a pull request and should
explain the reason for the change and its effect on contributors.
